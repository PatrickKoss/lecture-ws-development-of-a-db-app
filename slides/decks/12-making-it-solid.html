MockMvc testet den HTTP-Rand

MockMvc führt Spring MVC ohne echten Netzwerkport aus. Die Use Cases liefern kontrollierte Daten. Wir prüfen Status und JSON-Vertrag.

Ein MockMvc-Test

mockMvc.perform(get("/api/students"))
        .andExpect(status().isOk())
        .andExpect(jsonPath("$.students.length()").value(2))
        .andExpect(jsonPath("$.students[0].firstName").value("John"))
        .andExpect(jsonPath("$.students[1].firstName").value("Jane"));

Hinweis

Der Test prüft den Kursvertrag mit firstName.

Für den Kursvertrag angepasster Ausschnitt aus java/rest-simple/src/test/java/com/example/restsimple/adapter/in/web/StudentControllerTest.java
Der Mock liefert vorher zwei Students. Der Test prüft Status, Länge und die beiden Vornamen im vereinbarten Feld `firstName`.

Service-Test mit Mockito

Fachfall ohne HTTP und Datenbank
Mockito kontrolliert Antworten der Ports. Wir testen die Entscheidung im Service. Ein Test pro sinnvoller Regel ist wertvoller als einer pro privater Methode.

Ein Mockito-Test

when(saveStudentPort.saveStudent(any(Student.class))).thenReturn(expectedStudent);

// When
Student result = studentService.createStudent(command);

// Then
assertNotNull(result);
assertEquals("John", result.getFirstName());
assertEquals("Doe", result.getLastName());
verify(saveStudentPort).saveStudent(any(Student.class));
java/rest-simple/src/test/java/com/example/restsimple/application/service/StudentServiceTest.java, Zeilen 51 bis 60
Stub, Aufruf, zwei Zustandsprüfungen und eine Interaktionsprüfung sind sichtbar. Wir prüfen nur die Interaktion, die zum Fachfall gehört. Der Ausschnitt verwendet den Getter aus dem Kursmodell.

Was wir nicht testen

  • Status
  • JSON
  • Validation
  • Fachregeln
  • Fehlerpfade
  • Getter
  • private Methoden
  • Spring selbst
  • jede Logzeile
Tests kaufen Sicherheit für Änderungen. Triviale Getter und Framework-Verhalten liefern wenig Wert. Ein fehlender 404-Test ist dagegen ein echtes Vertragsloch.

Eine Correlation ID pro Request

Die gleiche ID steht in allen Logzeilen eines Requests. Ein Client kann sie bei einer Fehlermeldung nennen. Nach dem Request räumt der Filter MDC auf.

LoggingFilter

String correlationId = getOrGenerateCorrelationId(request);
        
try {
    MDC.put(CORRELATION_ID_KEY, correlationId);
    response.setHeader(CORRELATION_ID_HEADER, correlationId);
    
    long startTime = System.currentTimeMillis();
    logger.debug("Request started: {} {} - Correlation ID: {}", 
                request.getMethod(), request.getRequestURI(), correlationId);
    
    filterChain.doFilter(request, response);
    
    long duration = System.currentTimeMillis() - startTime;
    
    // Log basic timing info for all requests
    if (response.getStatus() >= 400) {
        logger.warn("Request failed: {} {} - Status: {} - Duration: {}ms - Correlation ID: {}", 
                   request.getMethod(), request.getRequestURI(), response.getStatus(), 
                   duration, correlationId);
    } else {
        logger.debug("Request completed: {} {} - Status: {} - Duration: {}ms - Correlation ID: {}", 
                    request.getMethod(), request.getRequestURI(), response.getStatus(), 
                    duration, correlationId);
    }
               
} finally {
    MDC.clear();
}
}

Drei Aufgaben

Correlation ID übernehmen oder erzeugen

in MDC und Response setzen

im finally löschen

java/rest-simple/src/main/java/com/example/restsimple/config/LoggingFilter.java, Zeilen 30 bis 59
Der Filter liegt vor dem Controller. finally verhindert, dass eine Thread-Wiederverwendung die alte ID trägt. Passwörter und Tokens gehören nie in detaillierte Logs.
