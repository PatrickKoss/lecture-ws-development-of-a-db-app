Nein, eine Klasse ohne eigene Entscheidung hilft nicht
Erwartet ist eine abgewogene Antwort. Typisch falsch sind "jede Architektur braucht drei Klassen" und "Services sind immer unnötig". Wir entscheiden nach Verantwortung.

Drei Schichten

Presentation kennt HTTP. Repository kennt Speicherung. Service koordiniert einen Use Case, wenn mehr als Weiterreichen passiert.

Wann der Service lohnt

Für unsere kleinste CRUD-Ressource kann direktes Speichern lesbar sein. Bei Enrollment mit Kapazitätsprüfung und zwei Schreibvorgängen gehört die Koordination in einen Service.

Entity nach außen ist eine Kopplung

Eine Entity ändert sich für Datenbankgründe. Ein API-Vertrag ändert sich für Clientgründe. Dasselbe Objekt koppelt beide Änderungsgründe.

Request DTO und Response DTO

Der Request erlaubt nur Eingaben. Der Response verspricht nur Ausgaben. Unterschiedliche DTOs machen Besitz sichtbar.

@Valid stoppt am Rand

public record CreateStudentRequest(
        @NotBlank @Size(max = 100)
        String firstName,
        @NotBlank @Size(max = 100)
        String lastName,
        @NotBlank @Email String email,
        @NotBlank @Pattern(regexp = "M[0-9]{7}") String studentNumber) {}

Hinweis

Die Regeln gehören zur gemeinsamen Vorlage und werden im Kurs begründet.

common-example/backend/src/main/java/com/example/restsimple/dto/CreateStudentRequest.java
Bean Validation prüft Form und einfache Grenzen vor dem Service. Wir begründen jede Regel am gemeinsamen Student-Vertrag. Das vom Server gesetzte enrollmentDate gehört nicht in den Request.

Validierung hat zwei Orte

Syntaxnahe Regeln liegen am Request. Fachliche und konkurrierende Regeln brauchen Service oder Datenbank. Ein Unique Constraint bleibt nötig, auch wenn Java vorher prüft.

Statuscode aus einer Exception

Der Controller muss nicht jeden Fehler lokal fangen. Ein zentraler Handler übersetzt bekannte Exceptions konsistent. Unbekannte Fehler werden mit Correlation ID geloggt. Der Client erhält bei 500 weder Exception-Text noch Stacktrace.

@RestControllerAdvice

@ExceptionHandler(ResourceNotFoundException.class)
@ResponseStatus(HttpStatus.NOT_FOUND)
ApiError notFound(ResourceNotFoundException ex) {
    return new ApiError(
        ex.code(), ex.getMessage(), correlationId(), Map.of());
}
C2-Starter · GlobalExceptionHandler.java · Hilfsmethode ausgeschrieben
Die Handler-Methode verbindet Exception-Typ, Body und Status. Alle Controller erhalten dasselbe Verhalten. Ein 500-Handler loggt die technische Ursache, gibt sie aber nicht an den Client zurück.

Ein stabiler Fehlerkörper

C2-Starter · ApiError.java · fields hier ausgelassen
`code` ist der maschinenlesbare Vertrag. `message` bleibt für Menschen. Die Correlation ID verbindet Antwort und Log. Bei Validierungsfehlern enthält fields die Meldungen je Request-Feld. Bei 500 bleibt die technische Exception ausschließlich im Log.

Statuscodes aus Fachfällen

Wir wählen Status aus dem Fall, nicht aus der Exception-Hierarchie. 409 passt, wenn die Eingabe formal gültig ist, aber mit vorhandenem Zustand kollidiert.

Naming hält Ebenen lesbar

Ein Begriff pro Ding reduziert Übersetzungsfehler. Java nutzt camelCase, SQL snake_case. Abgesehen von dieser Schreibweise bleiben die Namen im gemeinsamen Beispiel gleich.

Hexagonal als größeres Bild

Das vollständige rest-simple trennt Use Cases von Adaptern. Der Kern kennt HTTP und JPA nicht. Eure Übung darf bei drei Schichten bleiben.

Derselbe POST in drei Schichten

Jede Schicht übersetzt eine andere Grenze. Der Controller spricht HTTP, der Service Fachfall und Transaktion, das Repository Persistenz. In unseren ORM-Übungen bleibt der Service auch für CRUD die Transaktionsgrenze.

UNIQUE bleibt die letzte Prüfung

C3 · ORM und Datenbank-Constraints
// Service: verständlicher Fachfehler
if (repository.existsByIsbn(command.isbn())) {
    throw new ResourceConflictException("ISBN_EXISTS", "ISBN vergeben");
}

// ORM-Adapter: schreiben und Datenbank-Constraints auslösen
return data.saveAndFlush(BookJpaEntity.fromDomain(value))
    .toDomain();
Bibliothekslösung · Ausschnitte aus zwei Schichten
Zwei Requests können gleichzeitig eine freie ISBN sehen. Deshalb bleibt UNIQUE in der Flyway-Migration nötig. saveAndFlush löst das SQL innerhalb des Repository-Aufrufs aus. Der Adapter übersetzt Constraint-Fehler, der globale Handler antwortet mit 409 und ApiError. SQL-Text und Stacktrace gehören ins Log. Ein Mock kann diesen Datenbankfall nicht belegen; dafür prüfen wir die echte SQLite-Datenbank.

Abgabe: POST 201, Validation 400 und Konflikt 409
POST verwendet dieselbe flache Hauptressource wie die GET-Endpunkte aus C2. Die Gruppen schreiben Request-Konvertierung, Repository-Zugriffe, Konfliktregel und Controller-Methode. Infrastruktur und Fehlerübersetzung sind vorbereitet. Ein Beispieltest zeigt das Muster; die Fehlerfälle schreiben die Gruppen selbst. PUT oder DELETE ist eine Vertiefung durch alle betroffenen Schichten.

Debrief, ein Request durch alle Schichten

Eine Gruppe verfolgt ihren schwierigsten Fehlerfall. Wir prüfen, ob der Response DTO und ApiError stabil bleiben. Wir zählen keine Klassen, sondern Verantwortungen.

Vertragstest gegen Entity-Änderung

Das ist der konkrete Gewinn der DTO-Grenze. Eine Persistenzänderung wird nicht versehentlich API-Änderung. Tests können den Response-Vertrag festhalten.
